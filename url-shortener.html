Overview

Project Details

I built this URL shortener to deepen my understanding of caching strategies and optimize redirect performance. The concept is straightforward—paste a long URL, get a short one—but the real focus was on building something that could handle traffic efficiently.


I also implemented rate limiting using Redis to manage traffic and ensure consistent performance. Each IP address is capped at 30 requests per minute using a sliding window counter. Once the limit is hit, the API returns a 429 (Too Many Requests) response until the window resets. This helps maintain service reliability under heavy load.


Redis serves as the caching layer, allowing most redirects to bypass the database entirely. The backend uses Hono running on Bun, which offers strong performance compared to traditional Node.js frameworks. For persistent storage, I chose Neon's serverless PostgreSQL for its simplicity and automatic scaling.


Beyond the current implementation, I used this project to think through how the system would scale. At higher traffic volumes, I'd introduce a load balancer to distribute requests across multiple server instances. The Redis layer would shift to a cluster setup for redundancy, and I'd consider a CDN for geographic distribution. Database reads could be offloaded to read replicas, keeping the primary instance focused on writes. While these aren't implemented here, designing with scale in mind helped me understand the decisions behind real-world URL shorteners like Bitly or TinyURL.
